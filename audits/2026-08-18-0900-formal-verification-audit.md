### Executive Summary

Audit of the `guide-architecture-design` skill and its associated reference documentation (`operating-contract.md`, `workflow-modes.md`, `gates-recovery-and-git.md`, `decision-capture-and-sync.md`) revealed critical vulnerabilities in state machine transitions, mutation integrity, and git execution boundaries.

### 1. Contradictions & Desynchronization

#### 🔴 [C1] Deadlock & Routing Contradiction in Implementation Readiness Gate Execution
- **Files & Lines:**
  - `SKILL.md:L3`, `SKILL.md:L15`
  - `workflow-modes.md:L11-L12`, `workflow-modes.md:L60-L63`
  - `gates-recovery-and-git.md:L67-L75`
- **Problem Description:**  
  In `SKILL.md:L3`, it is stated that this skill is used to apply an implementation readiness gate ("apply a current independent implementation-readiness gate"). `workflow-modes.md:L12` routes such requests directly to `READINESS_GATE` mode.  
  However, `gates-recovery-and-git.md:L73` requires that for `READINESS_GATE` to pass, a fresh independent `IMPLEMENTATION READY` verdict generated by the `audit-architecture-handoff` skill must ALREADY exist in the repository. At the same time, `SKILL.md:L15` and `workflow-modes.md:L11` mandate delegating readiness assessment to `audit-architecture-handoff` with guide termination.  
  **Consequence:** If the user requests "check readiness for implementation" from `guide-architecture-design` and an audit report has not yet been created, `READINESS_GATE` mode is guaranteed to return `BLOCKED` status and transition to `COMPLETE` without triggering or delegating the audit. A deadlock occurs.
- **Proposed Fix:**  
  Clearly delineate in `SKILL.md` and `workflow-modes.md` that `READINESS_GATE` is a passive check of a pre-existing audit artifact. If the audit verdict is missing or stale, the agent must return a block condition with an explicit instruction to the owner (or redirection) to run `audit-architecture-handoff` first.

#### 🔴 [C2] Local Git Fallback in Session-Branch Workflow Violates Mutation Boundaries & Preflight
- **Files & Lines:**
  - `SKILL.md:L19`, `workflow-modes.md:L58`, `gates-recovery-and-git.md:L63`
- **Problem Description:**  
  `workflow-modes.md:L58` and `gates-recovery-and-git.md:L63` allow a local fallback (`local git fallback`) when merging a session Draft PR branch into `main`.  
  However, executing a squash-merge locally requires running: `git checkout main`, `git merge --squash agent/session-<ID>`, `git commit`, `git branch -D`.  
  **Consequence:**  
  1) This directly violates `SKILL.md:L19` ("Do not ... perform direct unconfirmed pushes to primary production branches" / mutation restrictions on `main`).  
  2) Switching branches (`git checkout main`) alters `.git/HEAD` and the working directory during session closing, bypassing zero-write preflight rules, as preflight verified the session branch state, not `main`.  
  3) No check exists for desynchronization between local `main` and remote `origin/main`.
- **Proposed Fix:**  
  Eliminate unmanaged "local git fallback" for `main` when closing session PRs. If the `gh` CLI is unavailable, the agent must leave the Draft PR open, provide the local command to the owner, and record an incomplete merge gate, or specify a strictly preflight-verified local merge algorithm with cleanliness and freshness checks for `main`.

#### 🔴 [C3] Logic Conflict Between Mid-Batch Failure Containment and Autonomous Mechanical Retry
- **Files & Lines:**
  - `gates-recovery-and-git.md:L49-L56` ("Contain failure")
  - `gates-recovery-and-git.md:L57-L59` ("Permit a deterministic mechanical retry")
- **Problem Description:**  
  The "Contain failure" section (`gates-recovery-and-git.md:L49-L56`) unequivocally requires: upon an edit, validation, or commit error, STOP mutations, DO NOT clean up or alter partial state, and transition to `RECOVERY`.  
  The "Mechanical retry" section (`gates-recovery-and-git.md:L57`) permits an autonomous retry (mechanical retry) without re-confirmation from the owner (e.g., creating a missing directory or fixing a command typo).  
  **Consequence:** If during batch execution some files were already modified on disk and validation failed due to a command error, a retry modifies disk state during a failed batch. This creates a direct contradiction between the requirement to freeze state immediately (Contain failure) and permission to continue mutations (Mechanical retry).
- **Proposed Fix:**  
  Add a strict constraint to `gates-recovery-and-git.md:L57`: mechanical retry WITHOUT owner involvement is permitted EXCLUSIVELY during the preflight/dry-run phase BEFORE the FIRST disk write occurs. If even a single file has been modified on disk, automated retry is prohibited — transition to `RECOVERY` is mandatory.

### 2. Routing & Boundaries

#### 🟠 [M1] Unspecified Preflight Snapshot Update Rules During Intra-Batch Multi-File Mutations
- **Files & Lines:**
  - `gates-recovery-and-git.md:L8-L18`, `decision-capture-and-sync.md:L38-L48`
- **Problem Description:**  
  `gates-recovery-and-git.md:L18` requires re-verifying baseline immediately prior to writing. However, in a multi-file batch (e.g., syncing 4 specifications), after writing file #1, the Git working tree no longer matches the initial snapshot.  
  Preflight rules do not specify the baseline state update logic *within* a single batch between writes of individual files.  
  **Consequence:** The agent may either falsely react to its own modifications as external dirty state (external interference) and block the batch, or miss an invalid mutation due to incorrect disk qualification.
- **Proposed Fix:**  
  Formalize the incremental baseline footprint update step in `gates-recovery-and-git.md:L18`: when sequentially writing files within an authorized batch, the expected baseline hash/diff is automatically appended with the digest of the newly written batch file.

#### 🟠 [M2] Overlap & Ambiguity Between Direct Confirmation (`+`) and Mandatory Pushback on Architectural Risk
- **Files & Lines:**
  - `decision-capture-and-sync.md:L10-L13`, `decision-capture-and-sync.md:L29`
- **Problem Description:**  
  `decision-capture-and-sync.md:L29` states that short phrases like `+` or `OK` unambiguously confirm an active proposal.  
  However, `decision-capture-and-sync.md:L10-L13` obligate the agent to provide vigilant pushback (up to 3 attempts) whenever architectural or technical risks exist.  
  **Consequence:** If the owner sends `+` for an option containing explicit architectural risks (or an unsafe compromise proposed by the owner), the specification does not define priority between Rule 1 (`+` as unambiguous confirmation) and Section 4 (vigilant pushback). A vulnerability arises where dangerous decisions are captured instantly upon short `+` symbols.
- **Proposed Fix:**  
  Explicitly establish priority in `decision-capture-and-sync.md:L29`: Architectural vigilance and pushback have HIGHER priority than quick `+` qualification. If the confirmed option contains unresolved architectural risks, the `+` symbol is not treated as final confirmation until up to 3 pushback attempts have been conducted by the agent.

### 3. Edge Cases & Fault Tolerance

#### 🟠 [M3] Ambiguity in `DIRECT_SYNC` Qualification of "Durable Authority"
- **Files & Lines:**
  - `operating-contract.md:L22-L34`, `workflow-modes.md:L49`, `decision-capture-and-sync.md:L78-L79`
- **Problem Description:**  
  `workflow-modes.md:L49` allows `DIRECT_SYNC` mode without re-confirmation from the owner if the decision is "already confirmed in durable authority".  
  `operating-contract.md:L24` provides a list of authorities but does not define strict state metadata (e.g., meta-tags `ACCEPTED`/`APPROVED` vs `PROPOSED`/`DRAFT`).  
  **Consequence:** If a draft ADR or roadmap draft contains an unexecuted idea, the agent could mistakenly treat it as "durable authority" and execute `DIRECT_SYNC` with bulk specification updates without owner consent in the current session.
- **Proposed Fix:**  
  In `operating-contract.md:L24`, add a strict rule: An artifact is recognized as `durable authority` for `DIRECT_SYNC` ONLY if it possesses an explicit normative status of `ACCEPTED`, `APPROVED`, or `CONFIRMED` in its header/metadata. Any status of `DRAFT`, `PROPOSED`, or missing status requires `DECISION_CAPTURE` mode with confirmation.

#### 🟠 [M4] Predecessor Session Closing Vulnerability Without Owner-Supplied Timestamp
- **Files & Lines:**
  - `operating-contract.md:L50-L53`, `workflow-modes.md:L15`, `workflow-modes.md:L28`, `gates-recovery-and-git.md:L30-L33`
- **Problem Description:**  
  `gates-recovery-and-git.md:L30` forbids inventing end timestamps and silently closing session records belonging to others.  
  If an unclosed session remains in the project from a *previous conversation* (interrupted session) and the user requests "close the session", `workflow-modes.md:L28` mandates binding to the active session. If the agent attempts to close it using the current system clock (`observed_at`), it effectively invents a completion time for someone else's session from a prior conversation.
- **Proposed Fix:**  
  Specify in `gates-recovery-and-git.md:L32` that when closing an incomplete predecessor session from ANOTHER conversation, the completion timestamp MUST be explicitly provided or confirmed by the owner, or retrieved from the last validated host log.

#### 🟠 [M5] Under-Specified Recovery Algorithm for Pre-Existing Dirty Targets
- **Files & Lines:**
  - `operating-contract.md:L18`, `workflow-modes.md:L15-L19`, `gates-recovery-and-git.md:L13-L18`, `gates-recovery-and-git.md:L27`
- **Problem Description:**  
  If pre-existing uncommitted manual edits by the user exist in the project working directory in a file targeted by the current batch (e.g., `AGENTS.md`) prior to skill invocation, preflight blocks the batch. The skill transitions to `RECOVERY` but provides no concrete decision tree for integrating this dirty state.
- **Proposed Fix:**  
  Add a two-option recovery menu to `gates-recovery-and-git.md:L27`:  
  Option 1 (Owner commits/stashes their external edits),  
  Option 2 (Owner explicitly authorizes including the existing diff as the starting baseline for the current batch).

### 4. Data Integrity & Authority

#### 🟡 [m1] Exclusion of Feedback Artifact Paths in Zero-Write Batch Preflight Target Enumeration
- **Files & Lines:**
  - `SKILL.md:L51-L53`, `gates-recovery-and-git.md:L10`
- **Problem Description:**  
  `SKILL.md:L51` permits recording feedback (`observed` record) to a configured destination inside the project. However, `gates-recovery-and-git.md:L10` lists preflight paths but omits feedback artifact paths.
- **Proposed Fix:**  
  Add `feedback record path` to the list of paths validated by preflight in `gates-recovery-and-git.md:L10`.

#### 🟡 [m2] Missing GitHub CLI / Draft PR Failure Fallbacks in `SESSION_BINDING`
- **Files & Lines:**
  - `workflow-modes.md:L30`, `gates-recovery-and-git.md:L45`
- **Problem Description:**  
  `SESSION_BINDING` mode when working with a session branch requires executing push and creating an Eager Draft PR via `gh pr create`. No fallback actions are specified if GitHub CLI authorization is missing or network failures occur.
- **Proposed Fix:**  
  Add fallback algorithm: on `gh pr create` failure, preserve the local session branch, notify the owner, and continue in local mode without a Draft PR.

#### 🟡 [m3] Ambiguity in Timestamp Observation Reuse Across Multi-Turn Sessions
- **Files & Lines:**
  - `operating-contract.md:L49-L53`
- **Problem Description:**  
  `operating-contract.md:L50` specifies capturing a timestamp at the first tool call opportunity, but does not clarify whether the timestamp is updated during multi-turn tool invocations at closing.
- **Proposed Fix:**  
  Clarify: Session start timestamp is captured during binding (`SESSION_BINDING`), while session closing timestamp (`SESSION_CLOSING`) is read anew at tool execution during closing.
