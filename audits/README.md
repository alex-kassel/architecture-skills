# Architecture Skill Audit Registry & Standard

## Purpose

This directory maintains the durable evidence, prompt traceability, and implementation history of independent audits conducted on architecture skills. Every audit file is stored directly in `audits/` without subdirectories and contains complete provenance linking the initial prompt, the auditor's report, and the resulting triage/work resolution.

## Audit Naming Standard

All audit files MUST reside directly in `audits/` (flat directory structure) and use the chronological date-time naming convention:

```text
audits/
├── README.md                                  # Central audit registry and standard (this file)
├── YYYY-MM-DD-HHMM-<audit-name>.md           # Flat chronological audit document
└── ...
```

Example audit filenames:
- `2026-08-18-0900-formal-verification-audit.md`
- `2026-08-18-0905-architecture-dx-audit.md`
- `2026-08-18-1000-adversarial-chaos-audit.md`

## Mandatory 3-Block Audit Document Structure

Every audit document in `audits/` MUST be structured into three explicit blocks:

### 1. Header Metadata
```markdown
# [Audit Title]

- Target Skill: `skills/<skill-name>`
- Target Commit SHA: `<full-git-commit-sha>`
- Audit Date & Time: `YYYY-MM-DD HH:MM`
- Auditor Role: `<Auditor Role/Perspective>`
```

### 2. Block 1: Auditor Prompt (Промпт Аудитора)
Contains the exact text of the prompt provided to the independent auditor agent to initiate the audit.

### 3. Block 2: Audit Report (Отчет Аудитора)
Contains the complete, unedited audit findings and report generated by the independent auditor agent.

### 4. Block 3: Work Done & Resolution Report (Отчет о проделанной работе и Триаже)
Contains the detailed report of actions taken based on the audit findings, including a matrix of:
- Which findings were **accepted**, **rejected**, or **superseded** and why.
- Exact code/specification changes implemented in the skill.
- Verification evidence links (e.g. `evals/forward-tests.md` scenario IDs).

## Periodic Audit Triggers & 3-Way Audit Standard

### Independent Audit Triggers

An independent 3-way audit MUST be initiated when ANY of the following triggers occurs:

1. **Feedback Threshold Trigger:** After implementing **3 or more** accepted feedback items in a skill.
2. **Major Refactoring Trigger:** After any breaking change or structural refactoring of a skill's core reference files.
3. **Release Milestone Trigger:** Prior to publishing a new minor or major release tag of skill packages.
4. **Owner Explicit Request:** Whenever requested by the repository owner.

### Developer Community 3-Way Audit Standard

Independent audits cover three distinct perspectives:

1. **Side 1: Formal Logic & Safety (Formal Auditor)** — Zero-write preflights, boundary enforcement (V1 limits), routing determinism, atomic mutation rules, failure containment.
2. **Side 2: Architecture Alignment & DX (DX Auditor)** — Documentation-as-Code standards (MADR/ADR, C4), vendor neutrality, friction reduction, confirmation fatigue prevention.
3. **Side 3: Adversarial Chaos & Edge-Cases (Chaos Auditor)** — Interrupted contexts, dirty worktrees, network/CLI failures, conflicting user inputs, prompt injection resilience.

## Autonomous 3-Agent Audit Execution Protocol ("Проведи аудит")

When the owner issues the trigger command **"Проведи аудит"**, **"Start audit"**, or equivalent, the system automatically executes the following 4-phase, **2-pass iterative audit protocol**:

### 🔁 Mandatory 2-Pass Iteration Loop Policy

Every audit cycle MUST execute **at least two full passes**:
- **Pass 1 (Initial 3-Way Audit & Fixes):** Conduct initial 3-way audit (Formal, DX, Chaos), present triage, implement accepted fixes, and validate.
- **Pass 2 (Verification 3-Way Re-Audit):** Immediately launch 3 independent subagents to re-audit the updated skill code. Verify that Pass 1 fixes are complete, introduced no new regressions, and created no secondary contradictions.
- **Residual Deferral Gate:** Minor non-blocking findings identified in Pass 2 are documented and deferred to the next scheduled audit cycle to prevent infinite perfection loops while maintaining high velocity and safety.

---

### Protocol Execution Phases

1. **Phase 1: Document Initialization (Block 1)**
   - Generate 3 audit files directly in `audits/` using the date-time naming scheme (`audits/YYYY-MM-DD-HHMM-<perspective>.md`).
   - Populate Header Metadata and **Block 1: Auditor Prompt** with the tailored prompt for each of the 3 auditor roles.

2. **Phase 2: Concurrent Subagent Execution (Block 2)**
   - Launch 3 independent subagents concurrently via `invoke_subagent`.
   - Each subagent conducts a fresh-session audit of the target skill(s), writes its findings directly into **Block 2: Audit Report** of its assigned file, and completes.

3. **Phase 3: Triage & Owner Presentation**
   - Consolidate all findings into `feedback/20??-*.md` records.
   - Present a unified Triage Matrix to the owner with expert community-backed recommendations (`accepted`, `rejected`, `superseded`) and trade-off analyses for approval.

4. **Phase 4: Implementation, Validation, & Resolution Documentation (Block 3)**
   - Upon owner triage approval (`+`), apply accepted reusable fixes to `skills/`.
   - Run structural and forward-test validation in `evals/forward-tests.md`.
   - Mark feedback records `verified` and populate **Block 3: Work Done & Resolution Report** in all 3 audit files.
   - Register the audit run in `audits/README.md` central table and execute Pass 2 Re-Audit.
